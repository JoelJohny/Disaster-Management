1 · Entry and authentication

Everyone arrives at the same place. The account's role — not a choice the user makes — decides where they land and what they can reach afterwards.

On refresh provideAppInitializer calls GET /auth/me before the router starts. Without it every guard would bounce an already-signed-in user back to the login page on every page reload.

2 · The three journeys

Victim

Someone who needs help

  1. DashboardActive event, open requests, nearest shelter with space/victim/dashboard
  2. Request helpThree steps: details → location → describe/victim/submit-request
  3. …or one-tap SOSCritical rescue, no form, uses saved addressPOST /requests
  4. My requestsFilter pills with server-computed counts/victim/my-requests
  5. Request detailFull timeline; volunteer contact once accepted/requests/:id
  6. CancelOnly while still unacceptedPOST /requests/:id/cancel
  7. RateOnce completed, once only/victim/feedback/:id

Volunteer

Someone who can help

  1. Pending approvalCan look, cannot claim, until an admin approvesapproval_status
  2. DashboardAvailable nearby, active tasks, hours, rating/volunteer/dashboard
  3. Available requestsBy urgency then distance — victim identity hidden/volunteer/available-tasks
  4. AcceptAtomic claim; contact details released herePOST /requests/:id/claim
  5. My tasksStart → progress → complete, or release/volunteer/my-tasks
  6. CompleteLog hours; victim may now ratePATCH /assignments/:id

Administrator

Coordinates the response

  1. Operations dashboardLive KPIs, 7-day trend, activity feed/dashboard
  2. User managementApprove volunteers; guardrails on deactivation/admin/user-management
  3. All requestsFilter, search, assign a volunteer directly/admin/all-requests
  4. Disaster eventsCreate; state derived from dates, never stored/admin/disaster-management
  5. ReportsCategory × status cross-tab, CSV export/admin/system-reports

3 · One request, three people

This is the heart of the system. A single request moves between all three roles, and every move writes one row to request_status_events.

Five rows, three readers Those five transitions wrote five rows to one append-only table. That table draws Priya's timeline, Divya's activity feed and the audit trail. One write satisfies three requirements — and the application account has no UPDATE or DELETE privilege on it, so history cannot be rewritten.

The route guard is convenience, not security Hiding a menu item and blocking a navigation only tidies the interface. Every request is re-checked on the server: requireAuth is mounted on the whole /api/v1 router with a five-entry public allowlist, so an endpoint added without thought fails closed. Typing an admin URL as a victim gives a real 403, and so does curl with that victim's cookie.

┌─────────────┐ │ SUBMITTED │ ◀── victim creates it └──────┬──────┘ ┌─────────────┼──────────────┐ claim │ │ cancel │ victim only, and only while unclaimed ▼ ▼ │ ┌─────────────┐ ┌───────────────┐ │ │ ASSIGNED │ │ CANCELLED │ ◀┘ terminal └──────┬──────┘ └───────────────┘ │ └──────── release ──────▶ back to SUBMITTED start │ ▼ ┌─────────────┐ │ IN_PROGRESS │ └──────┬──────┘ │ └──────── release ──────▶ back to SUBMITTED complete │ ▼ ┌─────────────┐ │ COMPLETED │ terminal → the victim may rate it, once └─────────────┘
Release is what makes the guarantee reversible Setting an assignment inactive clears the generated column to NULL, which frees the unique index and returns the request to the pool. Unlimited closed assignments can coexist; only one may ever be open.
