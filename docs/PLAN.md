## Scope

The Disaster Relief Management System (DRMS) is a role-based web application connecting citizens affected by a disaster with approved volunteers and a district administrator, built as an Angular 20 single-page client served by an Express 5 / TypeScript API over a MySQL 8 database, with one Node process serving both halves on a single origin. Its scope is exactly one end-to-end relief workflow: a victim submits a located help request, the system auto-attaches it to the active disaster event covering that district, approved volunteers claim it under a database-enforced single-active-assignment guarantee, the assigned volunteer advances it through a server-validated status lifecycle and logs hours on completion, and the victim submits a one-per-request rating — with every transition written to an append-only event table that simultaneously drives the status timeline, the in-app notification bell, the administrative activity feed and the summary report. The system deliberately excludes out-of-band messaging (email/SMS/push), file and photo upload, interactive mapping, external geocoding and any cloud deployment, all of which are documented as Future Scope rather than silently omitted.

## Blockers to fix before writing code

### B1. schema.rawSqlSupplements item 4a (db/grants.sql)

**Problem.** `GRANT SELECT, INSERT, UPDATE, DELETE ON drms.* TO 'drms_app'@'%';` followed by `REVOKE UPDATE, DELETE ON drms.request_status_events FROM 'drms_app'@'%';` does not work. Verified on 8.0.46: `ERROR 1147 (42000): There is no such grant defined for user 'lens_app' on host '%' on table 'request_status_events'`. MySQL will not revoke a table-level privilege that only exists as a database-level grant. Because the official mysql image entrypoint runs with `set -eo pipefail` (confirmed at line 2 of /usr/local/bin/docker-entrypoint.sh) and executes each /docker-entrypoint-initdb.d/*.sql via `docker_process_sql`, this error aborts first-time initialisation. The container never reaches the healthcheck, the named volume is left half-populated, and on this laptop recovering means paying the 27-minute re-init. Note the devEnvironment artifact already contains the correct form — the two artifacts contradict each other and the SCHEMA one is wrong.

**Fix.** Never revoke; grant narrowly. The entrypoint has already issued `GRANT ALL ON `drms`.* TO 'drms_app'@'%'` (entrypoint line 322), so strip that first, then enumerate:

USE drms;
REVOKE IF EXISTS ALL PRIVILEGES ON drms.* FROM 'drms_app'@'%';
GRANT SELECT, INSERT ON drms.* TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.users              TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.volunteer_profiles TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.request_types      TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.disaster_events    TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.shelters           TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.help_requests      TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.assignments        TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.feedback           TO 'drms_app'@'%';
GRANT UPDATE, DELETE ON drms.notifications      TO 'drms_app'@'%';
-- drms.request_status_events deliberately omitted: SELECT + INSERT only
FLUSH PRIVILEGES;

I ran exactly this: SHOW GRANTS is correct, INSERT into request_status_events succeeds, UPDATE and DELETE both return `ERROR 1142 (42000): UPDATE command denied ... for table 'request_status_events'`. That 1142 is a thirty-second demo beat worth keeping. Table-level GRANT requires the table to exist, so grants.sql must stay numbered after schema.sql.

**Fix.** Declare the API CONTRACT `endpoints` array the single source of truth, then do a find-and-replace pass over FRONTEND WIRING and SCHEDULE before week 1. ### B6. API CONTRACT `zodContracts` → `CreateRequestBody.typeCode` vs FRONTEND WIRING `formsPattern` wizard submit

**Problem.** The backend schema declares `typeCode: RequestTypeCode` (a string enum: 'MEDICAL'|'FOOD_WATER'|…). The wizard builds a control `requestTypeId: [0, [Validators.required, Validators.min(1)]]`, binds `<option [ngValue]="t.id">` (a number), and POSTs `requestTypeId: v.details.requestTypeId`. Every wizard submission is a 422 on an unknown key plus a missing required key. The admin filter has the same split: Zod `typeCode?: RequestTypeCode` vs frontend `?typeId=`.

**Fix.** Pick codes, not ids, everywhere — they survive a reseed and read better in the CSV. Change the wizard control to `typeCode: ['' as RequestTypeCode | '', Validators.required]`, bind `<option [ngValue]="t.code">`, and change the admin filter query param to `typeCode`. Keep `request_types.id` as the FK internally; resolve code→id in `request.service.ts`.

### B7. API CONTRACT `errorModel` vs FRONTEND WIRING `core/util/form-errors.ts` and `core/models/api.models.ts`

**Problem.** The error envelope is specified as `{ error: { code, message, fieldErrors, details } }` and the Zod middleware builds `new AppError('VALIDATION_FAILED', 422, '…', fieldErrors)`. The frontend reads a different key: `const fields = (e.error?.error?.fields ?? {}) as Record<string, string>`, and `api.models.ts` declares `ApiErrorBody { error: { code; message; fields?: Record<string,string> } }`. Result: every 422 renders as a silent no-op — the form clears its banner, shows nothing, and the user has no idea why submit did nothing.

**Fix.** Standardise on `fieldErrors`. Change `api.models.ts` to `fieldErrors?: Record<string,string>` and `form-errors.ts` to `e.error?.error?.fieldErrors ?? {}`.

### B8. FRONTEND WIRING `formsPattern` section D vs API CONTRACT `zodContracts` CreateRequestBody

**Problem.** `applyServerFieldErrors` does `form.get(path)` and the note says "Backend Zod issue paths must be emitted dot-joined (`\"location.peopleCount\"`) so `form.get(path)` resolves straight into the nested group." But `CreateRequestBody` is FLAT — `peopleCount`, `description`, `locationText` are all top-level, so Zod emits `"peopleCount"`. The wizard FormGroup is NESTED (`details` / `location` / `describe`), so `form.get('peopleCount')` returns `null` and every server field error on the highest-traffic form in the app is silently discarded. The same mismatch applies to `description` → `describe.description`.

**Fix.** Keep the Zod schema flat (the API shape should not mirror a UI wizard) and add a path map to the wizard component: `const SERVER_PATH = { typeCode:'details.typeCode', urgency:'details.urgency', district:'location.district', locationText:'location.locationText', peopleCount:'location.peopleCount', description:'describe.description', contactPhone:'describe.contact', contactEmail:'describe.contact' }` and pass it as a second argument to `applyServerFieldErrors(form, err, SERVER_PATH)`. Delete the "emit dot-joined paths" instruction — it is wrong for this schema.

### B9. API CONTRACT `POST /api/v1/requests` notes (SOS payload) and `zodContracts` `CreateRequestBody.refine`

**Problem.** `CreateRequestBody` ends with `.refine(v => !!v.contactPhone || !!v.contactEmail, { message: 'Provide a phone number or an email so we can reach you', path: ['contactPhone'] })`. The SOS payload is specified as `{ typeCode:'RESCUE', urgency:'CRITICAL', district: me.homeDistrict, locationText:'SOS - saved home location', peopleCount:1, description:'Emergency SOS raised from the victim dashboard.' }` — no contactPhone, no contactEmail. **Fix.** Move the fallback server-side: in `request.service.ts`, `contactPhone ??= me.phone; contactEmail ??= me.email;` before the insert, and drop the `.refine` entirely (the account always has an email). If you keep the refine, it must run after the fallback, not in the schema. Also change the wizard label to "Safe Contact Number or Email" and drop "(Optional)", or state "defaults to your account email".

### B10. AGREED SCOPE `demoScript` item 1 ("PRE-FLIGHT, 30 MINUTES BEFORE") vs DEV ENVIRONMENT `demoDayRunbook` and `seedCommand`

### B11. MySQL SCHEMA `seedDataPlan` — volunteer aggregates vs assignment and feedback counts

**Problem.** The seed states its own invariant: "Each volunteer's hours_logged equals SUM(assignments.hours_logged), completed_count equals COUNT of their COMPLETED assignments, and rating_avg equals AVG of their feedback — because an examiner who adds up the numbers on screen and finds they disagree has found a more damaging bug than any missing feature." The numbers then fail it. Volunteer `completed_count` values are Arun 14, Sneha 9, Rahul 7, Fathima 5, Deepak 4 = **39**, but the seed creates only **18 COMPLETED** help_requests and "One per … COMPLETED (18)" assignment. **Fix.** Scale the profile aggregates down to match the data, not up. Set completed_count to Arun 5, Sneha 4, Rahul 3, Fathima 3, Deepak 2, Meera 1 (=18) and rating_count to Arun 4, Sneha 4, Rahul 3, Fathima 2, Deepak 1, Meera 1 (=15), then recompute hours_logged as the literal SUM of each volunteer's seeded assignment hours and rating_avg as the literal AVG of their seeded ratings. Then add the four-query consistency check the seed plan already describes to `scripts/db-verify.mjs` so it fails loudly if you edit the seed later.

### B12. DOCS PLAN `testCaseTable` TC-LST-12 vs MySQL SCHEMA `seedDataPlan` status mix

**Problem.** TC-LST-12 records as its Actual Result: `200; items 10; page 2; total 14; counts {SUBMITTED:14, ASSIGNED:9, IN_PROGRESS:6, COMPLETED:13, CANCELLED:3}`. This is presented in the graded Testing chapter as an observed result from a run that cannot have happened.

**Fix.** Rewrite TC-LST-12 to not filter by status: `GET /api/v1/requests?scope=all&page=2&pageSize=10` over 45 requests — expect items.length 10, page 2, total 45, counts summing to 45, ids disjoint from page 1. ## Remaining risks

- THE SCHEDULE IS STILL TIGHT AFTER EVERY ADJUSTMENT. With Day 0 at 5h, the two blank days, +3h for Chapter 7, +3h for UML and +2h for the literature survey, you land at roughly 84 of 85 available hours. - NOTHING IN THE 28 DAY-ENTRIES IS ALLOCATED TO DEBUGGING. Every hour is priced as producing something new that works first time, by a developer writing their first reactive form, first HTTP interceptor, first signal store, first JWT middleware, first MySQL transaction and first docker-compose file. The estimates read as if written by someone who had already done all of it once. Expect the real week-2 cost to exceed the plan even after the cuts, and treat the second-tier abort list as likely, not hypothetical.
- THE ATOMIC CLAIM HAS NO PLAN B. It is the project's technical centrepiece, it carries the viva, and no artifact says what to do if it is not working by the end of week 2. Write one now: if the transaction is not green by 4 Oct, fall back to the unique index alone with an optimistic INSERT-first-catch-1062 pattern (no FOR UPDATE, no winner name in the 409, just 'This request has already been accepted'). It is strictly weaker and you lose the friendly message, but the database guarantee — the part that actually matters — still holds and the race test still passes.
- THE REPORT HAS NO INTERNAL PRIORITY ORDER even after the cut to 80 pages. Under pressure the chapters that get thinned will be whichever ones are left, not the cheapest ones. Decide now which three sections you would sacrifice: I would nominate Ch5's sections 5.7-5.9, Appendix B, and Ch7's discussion prose (keep the figures and captions).
- UNVERIFIED AND WORTH TESTING EARLY: the lock-order deadlock was reported by a critique and is mechanically plausible, but I did not reproduce it myself. Test it explicitly in week 2 with two concurrent sessions before you rely on the fix. Similarly, the 'status COMPLETED implies completed_at IS NOT NULL' CHECK constraint suggested in one critique could reject a legitimate intermediate write inside the completion transaction — test it against the container before you add it, because a CHECK that breaks the happy path is worse than no CHECK.
- VOLUNTEER FAN-OUT IS UNCONSTRAINED. uq_one_active_assignment enforces one active assignment PER REQUEST; nothing stops one volunteer holding twenty simultaneously. If an examiner asks 'can Arun claim every request in the pool?', the answer today is yes. Decide before you are asked — either add the guard inside the claim transaction or state it as a deliberate choice, since surge relief workers genuinely do carry multiple tasks.
- THE permissions BLOCK ON /requests/:id HAS NO SPECIFIED RULES. The frontend plan leans on it hard ('it saves hours') but no artifact writes the boolean expressions. Write them into request.serializer.ts before week 2 or the one-component-three-roles claim quietly becomes three *ngIf ladders.
- scope=assigned CANNOT RETURN COMPLETED WORK AS SPECIFIED. The contract says 'JOIN assignments ON active_help_request_id (plus recently COMPLETED)', but that column is NULL once completed, so the join excludes exactly what the parenthetical promises. Demo step 14's completed task vanishes from My Tasks the instant it is completed. Fix the predicate explicitly.
- DURABILITY IS DELIBERATELY RELAXED and the report must not claim otherwise. innodb_flush_log_at_trx_commit=2 and innodb_doublewrite=0 are the right call for a disposable demo database and they are what makes db:reset 12 seconds instead of 90 — but Chapter 5 cannot describe the claim transaction as durable in the ACID sense while the server is configured to lose a second of committed work on a crash. One sentence handles it, and saying it first is better than being caught.
- THE 22 FOREIGN CONTAINERS ARE A STANDING HAZARD. I confirmed they are running right now, holding both port 3000 and port 8080. Even after you disable their restart policies, verify with `docker ps` after every Docker Desktop restart that only drms-* comes back. A Windows update that reboots the laptop the night before the demo will bring them all back if you only stopped them.
